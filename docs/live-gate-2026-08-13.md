## Defects surfaced (all pre-existing, none caused by this deploy's changes)

- **F1 — `python.replaceSchema` on C# components: appended Output refused at position 0.**
  `CanInsertParameter(GH_ParameterSide.Output, 0)` returns false on the freshly emitted C# script
  component (console `out` occupies/reserves the slot), so any exact-schema rebuild of a C#
  component fails: "The Python component rejected an appended Output socket at position 0."
  Hit twice. The Python path was live-gated long ago; the C# path had never been walked — the
  live-gate lesson verbatim.
- **F2 — SDK-source guard false-positive on `source:null` replaceSchema.** With `source:null` the
  adapter validates `beforeState.Source`, and a never-sourced C# scaffold still carries Rhino 8's
  FACTORY default template (`class ... : GH_ScriptInstance` + `RunScript`) — the guard then
  refuses the component's own default text ("C# sources must be Rhino 8 script-mode…"). The model
  did nothing wrong; the rebuild path is unusable for pristine C# scaffolds.
- **F3 — harness/UX**: a turn ending in `ask_user` leaves the session `idle` with NO assistant
  message, and `dev-wave.ps1` then grades `gate: PASS` — misleading; the wave report should
  surface a pending ask card. (Two waves here "passed" while actually parked on a question.)
- **F4 — bake_manager skill friction**: the skill's five auxiliary inputs are non-optional; unwired
  they fail GH data collection ("Input parameter layer failed to collect data") and the script
  never runs — outputs empty with no runtime error. Cost three waves + two ask cards to converge.
  Skill header should instruct wiring panels (or marking optional), and/or the component should be
  authored with optional auxiliaries. (Initially misdiagnosed as the W2 empty-output defect — it
  is not; the W2 item remains separately open.)

## F1/F2 — root-caused, fixed, and re-gated PASS (same day)

Headless probes (`scripts/research/probe-csharp-replaceschema*.py`, evidence in
`artifacts/dev-loop/probe-replaceschema*.json`) pinned both:

- **F1 root cause — runtime-agnostic, not C#-specific.** The script-parameter model
  (`RhinoCodePlatform.GH.IScriptComponent.Outputs`) NEVER contains the managed console `out`
  (probed identical on python3 and csharp), while `CanInsertParameter(Output, 0)` is always false
  (RhinoCode reserves slot 0 for the console). `AppendMissingParameters` used the script-model
  index as the GH insert position, so a freshly cleared replacement (script outputs = [])
  appended its first output at GH position 0 → always refused. **python.replaceSchema with any
  declared outputs was equally broken — it had simply never been walked by a live gate.** On the
  setSchema path the same off-by-console insert landed mid-list and was silently masked by the
  positional-reconcile rename machinery. Fix: appends are anchored to the END of the live GH
  parameter list (`Params.Input/Output.Count`), the only positions CanInsertParameter/Register
  actually govern.
- **F2 fix**: the SDK-wrapper guard in replaceSchema now applies to MODEL-SUPPLIED source only;
  `source:null` inherits the stored text (a pristine scaffold's factory class template compiles
  fine and no longer trips the refusal).

Re-gate (session `15eeeb48`, run `20260813T155926Z-3230d91e`): C# ExactShape scaffold →
exact-schema replaceComponentIo (no inputs, output `a`) → execute → **a = 42 verified from
committed output inspection**; Python PyExact same flow → **b = 7 verified**. 7 commits, zero
failures. (One non-blocking observation repeated: the model's hand-authored `gptino:auto
outputNonEmpty` predicate mis-targeted the replacement's resource on its first try — standard
"omit acceptancePredicates" guidance resolved it; contract-friction, not a server defect.)

## W2 — measurement-driven predicted-solve gate: implemented and live-gated PASS (same day)

Implementation (commit follows this doc): per-(docKey, componentId) measurement table — last
python.execute wall-clock, the input volume that solve consumed, per-output item counts from every
job's Verify inspection — held in memory and mirrored durably (`component-measurements.db`,
restart-hydrated, Save-As-remapped). At execute preflight the gate refreshes the target's DIRECT
upstream output counts with a capped live inspection (8 owners — table counts alone go stale the
moment a slider expands an upstream no job's writeSet touches), then blocks when
`lastSolveMs × currentItems/lastItems > 20s` (D2). Execute-record path runs the same refresh so
the calibration pair is coherent.

Live gate (sessions `34caa65c`, `1e050c96`): calibrate Stage2 (10k-sin per item) at count=400
(~41-50 ms, committed) → raise the count slider to 400,000 → execute attempt REJECTED before any
write. First run exposed a calibration-coherence defect (basis recorded as "~10 items" from a
Series inspected at creation-default count → prediction overestimated ~40×, safe direction);
after the record-path refresh fix the message reads exactly as designed:
`predicted to take ~50.0s (its last measured solve was 50 ms on ~400 input item(s); the currently
wired input volume is ~400,000 item(s) across 1 measured source(s)) — over the 20s
predicted-solve ceiling`. Note the slider-product gate cannot see this case at all (the count
slider feeds the Series, not the executed script) — precisely the gap W2 closes. The F1
replaceSchema fix re-verified incidentally in the same runs (C# exact-schema rebuilds committed).

Known limits (documented, accepted): a slider change batched INTO the same ChangeSet as the
execute is not yet visible to the live refresh (pre-dispatch reads see pre-change counts); scaling
assumes ~linear per-item cost (superlinear code under-predicts) — both remain the watchdog's job.

## W3 — consolidation lifecycle: implemented and live-gated PASS (same day, evening)

Implementation (commit follows this doc): `CSharpStageMerger` (deterministic Roslyn merge — using
hoist, collision rename with member-position refusal, seam assignments between marker blocks,
single-line meta header, byte-exact Compose∘TryParseLayout round-trip), `consolidate_stages` host
tool (merge: plan/cap-math/dryRun → CS create → exact-schema replaceSchema with a comment-only
stub → wires → setSource+execute → field-wise output equivalence vs the old sink → consumer rewire
→ stage deletion in its own destructive-intent ChangeSet; split: the mechanical inverse, verified
the same way before the merged component is deleted), and `python.replaceBlock`
(OperationKind.ReplaceSourceBlock — a server-side MACRO validated as its own kind and rewritten at
dispatch into python.setSource carrying the recomposed source with the read's concrete sha as CAS;
no bridge/protocol change, watchdog re-injects through the existing setSource hook).

**F5 — found by this gate and fixed same-day (the fixture-vs-reality class):** Rhino 8 script-mode
PRE-DECLARES socket variables, so real model sources ASSIGN their outputs (`pts = list;`) — they
never declare them. The merger's first version required a top-level declaration and refused the
very first real chain. Fix: non-sink outputs' first top-level assignment is PROMOTED to a
declaration at merge (branch-only/self-referencing assignments still refuse with an actionable
message), split DEMOTES declarations of a stage's own output names back to assignments, and the
scaffold stubs became comment-only (a declaring stub would collide with the implicit socket
declarations). Also fixed before the pass: both scaffold paths must declare schemas via
replaceSchema — setSchema's append-only contract can never fit a fresh component's factory
sockets (x, y, a) to an arbitrary merged schema.

Known limits (documented, accepted): C# stages only; single-sink connected groups; top-level type
declarations refused; consumer code compiled against a hinted input type now sees the producer's
concrete type (a mismatch surfaces in the equivalence check, which discards the merged component);
the dynamic-tool 30s deadline bounds one apply call (phases run server-side; job_status recovers
the state if the call itself times out).
